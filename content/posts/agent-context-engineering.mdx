假设一个 Agent 正在修复接口超时问题。它先读取项目规范，再搜索调用链、检查日志、修改代码，最后运行测试。任务进行到一半，它却重新打开已经检查过的文件，重复尝试刚刚失败的命令，甚至忘记用户要求保持接口兼容。相关信息可能仍在对话历史里，只是混在大量代码和日志之间，没能在下一次决策中发挥作用。

李博杰在《深入理解 AI Agent：设计原理与工程实践》第二章中，将这类问题放到上下文工程的框架下讨论：每次调用模型前，需要决定哪些信息进入请求，以什么结构呈现，什么时候更新，以及哪些历史可以压缩。[1]

沿着一个任务的执行过程看，提示词、工具结果、Skills 和状态摘要都有各自的生命周期。把这些信息组织好，既关系到模型能否继续完成任务，也关系到长对话的推理成本。

## 1. 上下文的组成与执行循环

模型要修复一个项目中的问题，需要了解当前代码、运行环境、业务约束和已经完成的操作。这些信息即使保存在磁盘或数据库中，也不会自动成为本轮决策的依据。Agent 的运行框架需要通过读取、检索和状态整理，将相关内容放入模型能够处理的请求。

书中以结构化消息接口解释这一过程：开发者指令提供规则，用户消息表达目标，助手消息记录回复与工具调用请求，工具结果反馈执行情况；工具定义则说明可调用的能力及参数。工具定义可能是请求中的独立字段，不能仅凭消息列表的长度判断完整的上下文成本。[1]

对前面的代码修复任务，稳定指令与持续增长的执行历史共同构成本轮输入。模型发出工具调用请求后，由运行框架校验、执行，再将结果和更新后的状态用于下一次调用。

每一轮都需要保留足够的信息，使模型知道刚刚发生了什么。尤其是工具调用请求与执行结果之间的对应关系，应当按照所用接口的协议维护。只保留“测试失败”几个字，可能不足以判断失败的是哪个用例；只保留一段工具输出，却删除对应的调用参数，也可能失去理解结果所需的条件。

这些结构化消息还会经过模型对应的聊天模板，转换成实际输入的 token 序列。角色、消息边界和工具调用结构都属于这个转换的一部分。书中由此强调，应当保留接口要求的消息结构，避免把所有内容拼成一段看似完整、实际丢失来源和关联关系的文本。[1]

这也解释了上下文与记忆的区别。当前请求中的内容直接参与本轮推理；外部保存的日志、笔记和知识库，需要经过选择和读取才能参与决策。即使服务端提供会话管理，也仍然需要明确本轮究竟使用了哪些历史信息。

## 2. 缓存复用与前缀稳定性

多轮任务会重复使用大量相同内容：项目规则没有变化，工具定义没有变化，前几轮读过的文件也仍在历史中。如果每次请求都重新处理这些内容，输入处理成本就会不断累积。

书中区分了两个层次的缓存。KV Cache 保存推理过程中已经计算过的 Key、Value 状态，减少生成后续 token 时对历史状态的重复计算；跨请求的前缀缓存则尝试在多次调用之间复用这些状态，通常也称为 Prompt Cache。前者是推理机制，后者还涉及服务端的缓存管理与复用策略。[1]

对于本章讨论的因果注意力模型，一个位置的状态依赖它自身及前面的输入。因此，复用缓存时关注的是实际 token 序列的共同前缀。某个位置发生变化后，该位置及其后续状态通常需要重新计算；变化之前的前缀仍可能复用。不能把这个过程理解为“改动一个字符，所有缓存都会失效”。[1]

假设系统指令后面还有一长段工具定义和任务历史，每轮却在指令开头更新当前时间，那么变化点会很靠前。即使后面的文本没有改动，也无法继续直接复用原先完整的前缀状态。将时间这类动态信息按需加入后面的消息，可以保留更多共同前缀。同样，工具定义的排列、固定示例和规则文本，都应避免无必要的逐轮改写。

这里的“稳定”需要服从任务正确性。权限已经变化、规则发现错误，仍然需要及时更新；缓存命中不能成为保留错误信息的理由。按需选择工具或检索材料也可能值得付出部分重算成本，判断依据应是整项任务的效果与开销。

缓存还不等于免费处理长上下文。对于常规稠密注意力，即使历史 K、V 已经存在，生成新 token 时仍需要利用历史缓存完成注意力计算，长输入也会占用更多缓存资源。跨请求能否命中、缓存保存多久以及如何计费，则取决于具体服务的实现。它解决的是重复计算问题，不能代替会话存储或上下文压缩。

## 3. 系统规则与领域能力的分层

稳定前缀适合承载跨任务通用的规则，但不适合无限扩充成一份覆盖所有场景的操作手册。代码修复、数据分析和文档排版的详细流程如果同时常驻，每个任务都要承担大量无关信息的成本。

第二章介绍的 Skills 采用渐进式披露：先让模型看到名称和适用条件，需要时再加载核心流程，遇到具体问题后继续读取参考文档、模板或脚本。这样，能力仍然可被发现，详细内容的加载时机则由当前任务决定。[1]

以代码修复为例，通用规则可以说明修改范围、兼容要求和交付标准；调试 Skill 再提供复现、定位和验证流程；具体框架的排查手册只在问题涉及该框架时读取。三层信息分别回答“始终要遵守什么”“这类任务如何开展”和“当前细节如何处理”。

Skill 的描述因此需要写清触发条件。仅写“帮助处理代码问题”，很难区分开发新功能、分析异常和审查修改；写清适用任务、所需输入与输出，才能让模型判断是否值得加载。核心流程也应包含完成条件和异常分支，避免只有背景知识而缺少可执行步骤。

Skill 与工具承担的责任不同。Skill 提供方法和约束，工具负责读取文件、运行测试或执行查询。详细的使用说明不会自动改变执行权限，加载一份 Skill 也不意味着其中提到的全部动作都已获得授权。

从缓存角度看，详细指令可以在首次需要时加入轨迹，后续保留在原位置，避免每轮把同一段内容移到最新消息后面。目录和正文具体使用什么消息角色，由运行框架决定；渐进式披露并不要求所有实现采用相同的消息包装方式。[1]

信息分层还需要保留来源。项目规则、用户要求和外部文档不能在整理后混成同一种指令。书中讨论了提示注入：文档或工具结果里可能包含试图改变 Agent 行为的文本。来源标记有助于区分资料与指令，但不能替代执行层的权限检查，也不应被当作完整的防护保证。[1]

## 4. 任务状态的显式维护

执行历史记录了发生过的事情，当前状态则概括了任务现在处于什么位置。两者有关联，但不必让模型在每次决策前都重新从长历史中推算状态。

代码修复任务中的测试是否完成、哪些文件已经改动、同一命令失败了几次，都适合显式维护。书中将这类运行时摘要称为 Agent 状态栏。它的目的，是让模型直接获得任务进度和约束，减少反复扫描历史的负担。[1]

下面是一份用于说明结构的状态示例，其中的路径、次数和结论均为假设数据：

```json
{
  "revision": 8,
  "goal": "修复接口超时，保持现有响应格式",
  "phase": "验证",
  "confirmed": ["已复现连接获取超时"],
  "hypotheses": ["连接释放路径可能存在遗漏"],
  "changed_files": ["src/client.py"],
  "test_attempts": 2,
  "last_test_status": "failed",
  "next_step": "检查失败日志，再决定是否调整实现"
}
```

这个结构有意分开了确认事实与待验证假设。“发现了可疑代码”不能直接写成“已确认根因”，“发出了测试命令”也不能写成“测试通过”。计数、退出状态和文件变更等可确定的信息，应当尽量从实际事件中生成；需要模型归纳的判断，则保留证据和不确定性。

状态更新会带来新的布局选择。每轮删除旧摘要、加入新摘要，可以让上下文只保留一份当前状态，但删除位置之后的缓存可能需要重建。保留旧摘要、仅追加新摘要，更有利于前缀复用，却会累积过期信息。书中明确讨论了这两种方案的取舍：需要同时考虑摘要长度、更新频率和两次更新之间新增的内容。[1]

版本号能够帮助区分新旧状态，却不能保证模型一定忽略旧结论。若旧摘要不断积累，还需要在适当时机归档或合并。剩余配额、禁止执行的操作等硬性边界，则应由运行框架检查，不能仅靠状态文字提醒。

状态摘要也不能覆盖所有后续问题。知道测试失败了两次，并不能解释两次失败是否由同一原因引起。原始日志仍应可以回查，摘要负责降低日常决策成本，证据负责支撑进一步核验。

## 5. 任务感知的上下文压缩

随着任务推进，搜索结果、代码片段和日志逐渐占据上下文。最直接的压缩方式是只保留最近几轮，但早期信息的价值并不一定低：接口兼容要求可能来自第一条消息，某条已排除的失败路径可能决定下一步不该重复尝试什么。

压缩的目标应当围绕后续决策确定。对同一段日志，排查超时需要保留时间顺序、错误类型、调用位置和执行条件；编写变更说明则更关注修改原因与验证结果。书中把查询意图和已知信息一起纳入压缩过程，称为上下文感知压缩。[1]

仍以代码修复为例，一份只有“读取了文件，修改了代码，测试失败”的摘要，虽然很短，却无法支撑任务继续。更有用的记录应当保留复现条件、已确认事实、尚未证实的推测、已经尝试但无效的方案，以及下一步需要检查的证据。

这里尤其容易丢失的是条件和否定信息。“并发请求下出现超时”压成“请求超时”，会失去复现条件；“尚未验证连接泄漏”压成“连接泄漏”，会把假设变成结论。压缩前后的文字都通顺，并不代表语义仍然一致。

因此，大体积证据可以外置保存，再在摘要中保留定位信息。例如记录日志产物标识、相关行范围、代码提交与文件路径。后续遇到摘要未覆盖的问题时，再读取相应原文。仅保留一个可变文件路径并不总能恢复当时的证据，重要材料还需要对应版本或快照。

这种设计使“当前窗口保留多少内容”与“原始信息是否仍可获得”分开。压缩可以有损，但损失的细节应当尽可能可回查。连续压缩摘要时还要防止信息逐轮变薄：对关键约束和事实，必要时从原始记录重新整理，而不是始终在上一次摘要上继续删减。

书中用“检索与提炼”的关系解释状态维护和压缩的价值。工程上可以据此减少重复统计和归纳，但不宜进一步推导为模型只能检索、不能推理。更直接的判断是：已经能够可靠计算的事实，没有必要在每轮调用中重新计算。

## 6. 压缩时机与上下文预算

压缩通常会修改历史中的某个位置，因此也会牺牲部分缓存复用。它带来的收益是缩短后续输入、减少无关信息，代价则包括摘要调用、前缀重算和可能的信息损失。需要比较的是任务剩余过程的总成本。[1]

如果下一步即将结束任务，专门发起一次大规模摘要未必划算；如果还要执行很多轮搜索和验证，适当压缩可能减少后续反复携带旧材料的开销。仅用“压缩后的文本变短了”判断优化成功，会忽略摘要本身和重新检索的成本。

上下文预算还必须给后续动作留下余量。当前输入刚好低于窗口上限，不代表下一轮仍然能运行：模型输出、待返回的工具结果，以及协议要求保留的其他内容，都可能继续增加占用。预留空间应根据所用模型和接口的计算方式确定，不能把某个固定使用率当成通用阈值。

第二章提出分层处理的思路：先限制工具返回量，让大结果以预览和可回查产物的形式进入任务；再清理已经确认无用的材料；仍然接近预算时，对较早的阶段记录进行摘要。全量压缩可以作为后续手段，但也需要限制失败后的重复尝试。[1]

落到代码修复任务中，搜索工具可以先返回匹配位置与少量上下文，读取工具再获取相关函数，测试工具优先给出退出状态和失败用例，并附完整日志位置。这样能够在信息进入主上下文之前减少冗余，而不是每次都先接收整份输出，再依赖模型摘要。

压缩还要保护消息结构。如果后续仍保留某次工具结果，就需要检查理解它所需的调用关系是否完整；正在进行的工具交互也不能随意截断。历史归档后，应形成符合接口要求的完整记录，而不是仅按字符数裁剪消息列表。

## 7. 子任务隔离与信息回传

有些工作本身会产生大量临时材料，但最终只需要一个较小的结果。例如在多个模块中寻找超时处理路径，主任务需要的是相关位置、调用关系和证据，不一定需要保留全部搜索过程。

书中提出用子 Agent 的独立上下文承接这类探索。主 Agent 发出任务，子 Agent 完成检索与分析，再将结果返回主任务。这样可以减少进入主上下文的中间材料，降低后续整理历史的压力。[1]

隔离的前提是任务描述足够完整。仅要求“找一下超时问题”，子 Agent 不知道目标接口、仓库版本、已经排除的原因以及允许的修改范围。任务输入应包含完成当前子任务所需的背景，返回结果则应包含结论、证据位置和未解决的问题。

例如，一个搜索子任务可以返回“连接在正常路径释放，但异常分支需要继续检查”，并附具体文件、函数及相关调用点。只有“问题在连接池”这样的结论，会让主 Agent 失去核验依据，还可能把初步判断当成事实继续修改。

上下文隔离也有成本。子 Agent 需要额外调用，交接摘要可能遗漏条件，不同任务之间还可能重复搜索。对于目标文件已经明确、只需一次读取的工作，直接执行通常更简单；对于范围较大、结果可以独立验收的探索，隔离更容易体现价值。主上下文变短，并不意味着所有 Agent 的总 token 消耗一定下降。

## 8. 上下文策略的验证

上下文工程需要通过完整任务评估。某种布局提高了缓存命中率，却让 Agent 漏掉用户约束；某种摘要压缩得很短，却引发重复读取，这些结果都不能仅凭局部指标判断。

沿用代码修复任务，可以固定代码版本、初始缺陷和验证用例，对比完整历史、任务感知摘要、显式状态等配置。每次只改变一项主要策略，并对相同任务重复运行，观察结果是否稳定。下面的指标适合一起记录，而不是各自独立优化。

| 观察维度 | 具体记录 | 用途 |
| --- | --- | --- |
| 任务结果 | 缺陷是否修复，兼容测试是否通过 | 判断最终工作是否完成 |
| 约束保留 | 压缩后是否仍遵守修改范围和接口要求 | 检查关键信息是否丢失 |
| 重复操作 | 相同读取、搜索和无效重试的次数 | 发现遗忘或状态失真 |
| 推理开销 | 主任务、子任务和摘要调用的总用量与延迟 | 避免只计算局部收益 |
| 证据恢复 | 能否找到摘要结论对应的原始记录 | 验证压缩后的可追溯性 |

测试任务还应包含容易暴露信息丢失的情形：关键约束出现在早期，途中出现一个已经排除的方案，压缩后需要重新解释失败原因，或者用户在后续修改了目标。它们比单纯把上下文填长，更能检验状态更新和信息保留是否有效。

第二章中的实验提供了理解机制的例子，但某项配置下的提升比例不能直接当作其他模型和任务的收益承诺。实际系统中，需要保留可复现的输入、上下文构造记录和验证结果，再决定哪些策略值得长期采用。

回到最初的接口修复任务，合理的上下文管理应使 Agent 始终能够确认目标、区分事实与假设、找到已有证据，并判断下一步还缺什么。规则、状态和历史各自承担清晰的职责，长任务才更容易沿着已有进展继续推进。
