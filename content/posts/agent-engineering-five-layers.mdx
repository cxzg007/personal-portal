> 这两年，"XX Engineering" 的新名词出现得比框架还快：Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering、Graph Engineering。它们看起来像是一堆各自为政的黑话，但如果你把它们按"控制的对象"排一次序，会发现这其实是**同一件事在五个尺度上的展开**。本文不做名词科普，而是回到第一性原理：每一层到底在控制什么，为什么必须是这个顺序，以及最上面那一层是不是真的通向未来。

## 一个不太舒服的起点：模型是个"猜下一个词的赌徒"

要讲清这五层，得先接受一个朴素到有点冒犯的事实：**大模型的本质是一个条件概率函数**。

给它一段文本，它输出"下一个 token 最可能是什么"的概率分布，采样一个，追加到输入里，再算下一个。就这样反复。它没有目标、没有记忆、没有手脚、也没有"这次任务干完了"的概念。所有你在产品里看到的"它好像懂了""它会自己查资料""它把活儿分给了另一个 Agent"，都不是模型本身的能力，而是**外部工程给这个概率函数套上的约束结构**。

这就是全部五层工程的共同起点。它们没有一层在改模型参数，每一层做的事情都可以概括成同一句话：

> **在模型之外，构造一个约束，让这个概率过程的输出更接近我们想要的结果。**

区别只在于：这个约束作用在多大的范围上。

从"一次推理"开始，往外一圈一圈扩：一次推理 → 一次推理的输入 → 模型与外部世界的边界 → 多次推理构成的循环 → 多个循环之间的关系。**这五个圈，就是五层工程。**

```text
┌───────────────────────────────────────────────┐
│ Graph      循环之间的关系（多个循环怎么组织）      │
│  ┌──────────────────────────────────────────┐ │
│  │ Loop     反复行动的节奏（一个循环怎么推进）  │ │
│  │  ┌─────────────────────────────────────┐ │ │
│  │  │ Harness  模型与世界的接口（能碰什么）  │ │ │
│  │  │  ┌────────────────────────────────┐ │ │ │
│  │  │  │ Context  喂进去的信息（看到什么）│ │ │ │
│  │  │  │  ┌───────────────────────────┐ │ │ │ │
│  │  │  │  │ Prompt  单次推理（做什么） │ │ │ │ │
│  │  │  │  └───────────────────────────┘ │ │ │ │
│  │  │  └────────────────────────────────┘ │ │ │
│  │  └─────────────────────────────────────┘ │ │
│  └──────────────────────────────────────────┘ │
└───────────────────────────────────────────────┘
```

想清楚这个嵌套关系，后面五节就只是把每一圈说透。

## 第一层 · Prompt Engineering：控制"单次推理"

**它控制什么：**在信息量不变的前提下，改变模型这一次的行为倾向。

**第一性原理：**模型输出的是条件概率 `P(输出 | 输入)`。既然输出完全由输入决定，那么**在不改模型的情况下，唯一能动的就是输入**。Prompt Engineering 是这个事实最直接的推论——你在调整的不是知识，而是**概率分布的形状**。

这解释了很多"玄学技巧"为什么真的有效：

- 让它"一步步想"，是在把一个需要跨越多个 token 的推理，摊开成一条它更容易走对的路径；
- 给它一个角色（"你是一位资深审稿人"），是在把输出分布挪到语料中该类文本聚集的区域；
- 给两三个示例，是在用格式的强约束压掉大量不合规的候选。

**边界在哪：**Prompt 能改变"怎么说"，改不了"不知道"。当模型缺的是**事实**而不是**倾向**时，无论怎么措辞都是徒劳——你在优化一个函数的形状，但它的定义域里根本没有你要的信息。

于是问题被迫外移一圈：**得把信息喂进去。**

## 第二层 · Context Engineering：控制"喂进去的信息"

**它控制什么：**在有限的窗口里，决定模型这一次能看到哪些信息。

**第一性原理：**上下文窗口是一种**稀缺资源**。这句话是这一层所有技术的源头。

窗口有限，意味着"把所有可能有用的东西都塞进去"从一开始就不是选项。于是这一层的全部工作，本质上是一道**资源分配题**：从一个远大于窗口的信息空间里，选出最小的、够用的子集。

- **检索（RAG）**：不预先塞，等到问了再按需取——把"存什么"和"用什么"解耦；
- **记忆**：把跨轮次需要保留的东西压缩成摘要或结构化条目，用少量 token 换长期连续性；
- **窗口管理**：裁剪、分块、重排，本质是在做优先级排序。

有一个反直觉但很关键的点：**窗口变大并不让这一层消失。** 因为注意力是在整个上下文上竞争的，塞进去的无关信息不是"中立"的，它会稀释信号，把关键内容挤到模型不太看的位置。这就是所谓"lost in the middle"。所以 Context Engineering 的目标从来不是"塞得更多"，而是**信噪比更高**。

**边界在哪：**信息可以被喂进去，但**世界不能被喂进去**。模型能读到"当前库存是 300"，却不能把库存改成 280；能读到代码，却不能运行它看是否报错。它被关在一个只读的玻璃罩里。

于是问题再外移一圈：**得让它能碰到外部世界。**

## 第三层 · Harness Engineering：控制"模型与世界的接口"

**它控制什么：**模型能触达哪些外部能力，以及以什么形式触达。

**第一性原理：**模型唯一的输出是**文本**。所以"让模型行动"这件事，在物理上只可能有一种实现方式：**把文本解释为动作**。

Harness（挽具）这个词很贴切——它是套在模型和世界之间的那副器具。它做三件事：

1. **把能力翻译成模型看得懂的描述**（工具名、参数、什么时候该用）；
2. **把模型吐出的文本解析成真实调用**（函数调用、SQL、shell 命令、HTTP 请求）；
3. **把执行结果翻译回文本**，送回上下文里。

这一层最容易被低估的地方在于：**工具的设计质量，直接决定模型的能力上限**。同一个模型，接一个含义清晰、粒度合适、报错信息可读的工具集，和接一堆语义重叠、参数暗示不明、失败只返回 `Error` 的工具，表现差距会大到像是两个模型。

原因还是回到第一性原理：模型是靠"文本里的线索"来决策的。工具描述就是线索本身。描述模糊 = 线索缺失 = 概率分布无法收敛到正确调用。**工具设计是这一层真正的技术含量，不是接口胶水。**

同时，这一层第一次引入了一个新的工程问题：**风险**。只读时最坏结果是答错，能写之后最坏结果是把生产库删了。权限边界、沙箱、可撤销性、审计——这些从来不是 Prompt 层的问题，但在 Harness 层是必须回答的问题。

**边界在哪：**能行动，不等于能完成任务。一次"想 → 做"解决不了需要试错的问题：代码跑失败了要改、检索没找到要换关键词、方案被否了要重来。**单次行动无法承载"逼近"这个过程。**

于是问题再外移一圈：**得让它反复来。**

## 第四层 · Loop Engineering：控制"反复行动的节奏"

**它控制什么：**一次任务里，模型行动多少轮、每轮之间怎么衔接、什么时候停。

**第一性原理：**复杂问题没有闭式解，只能**迭代逼近**。

这句话在数值计算里是常识，在这里同样成立。写一个能跑通的功能、查清一个陌生系统的行为、修一个只在特定条件下复现的 bug——这些任务的共同点是：**你无法在行动之前就知道正确答案**，只能行动、观察、修正。

所以 Loop 层不是"多调用几次模型"这么廉价的事情，它要回答三个真问题：

1. **什么时候停。**这是最难的。停早了任务没完成，停晚了要么烧钱要么死循环。终止条件必须是可判定的——测试通过、编译成功、返回码为 0、达到最大轮数——而不能是模型自己说"我觉得可以了"。
2. **每一轮怎么推进。**上一轮的结果如何进入下一轮的上下文？是全量累积（很快撑爆窗口），还是压缩成状态摘要（省 token 但会丢细节）？这是 Loop 层和 Context 层的接缝处。
3. **反思锚在哪里。**让模型自我批评是有用的，但前提是**批评要有外部依据**。基于测试输出的反思能收敛，基于"你再检查一遍"的反思大概率只是让它把错误答案说得更自信。

还有一个必须正视的数字事实：**误差会累积。** 假设每一步的成功率是 95%，听起来很高，但 20 步串起来就是 `0.95²⁰ ≈ 0.36`——不到四成。这解释了为什么长链路 Agent 在 demo 里很惊艳、在真实任务上很脆弱。Loop 层的可靠性工程（重试、校验、把长链拆成可独立验证的短链）不是锦上添花，而是**这一层能不能用的前提**。

到这一层，"Agent"这个词才第一次有了确切含义。我在[另一篇文章](/blog/graph-engineering-ontology)里用过一个等式，这里再引一次：

```text
Agent = Loop( LLM + Harness )
```

它说明了一件容易被误解的事：**Agent 不是一种模型，而是一种控制结构。** 换掉模型，Agent 还在；去掉循环，就只剩一次问答。

**边界在哪：**一个循环再稳，也只有一条时间线。当任务需要多个不同职责的执行单元协同——分析的、写代码的、审查的、跑测试的——它们之间的**依赖、顺序、并行、回退**这些关系，塞不进单个循环的线性历史里。你会发现自己开始在提示词里写"如果上一步是 X 那么你现在应该"，这是结构在向外溢出。

于是问题最后外移一圈：**得把循环之间的关系显式地表达出来。**

## 第五层 · Graph Engineering：控制"循环之间的关系"

**它控制什么：**多个执行单元之间的关系结构——谁依赖谁、谁能调谁、状态怎么流转。

**第一性原理：****关系一旦存在，就必须被表达在某个地方。** 你不显式建模它，它不会消失，只会隐式散落在 if-else、提示词的措辞和开发者的脑子里。

这是 Graph Engineering 唯一的、也是充分的理由。图不是因为"图很酷"才出现，而是因为**关系是一种数据**，而表达关系最自然的结构就是节点和边。

```python
# 关系不再藏在提示词里，而是成为可读、可测、可改的一等公民
graph.add_node("analyze", analyze_requirement)
graph.add_node("implement", write_code)
graph.add_node("review", review_code)
graph.add_edge("analyze", "implement")
graph.add_conditional_edges(
    "implement",
    lambda state: "review" if state["compiled"] else "implement",  # 显式的失败回退
)
```

显式化带来的收益是很实在的：流程可以被画出来、被 review、被单元测试；失败可以定位到具体节点而不是"整个 Agent 挂了"；并行分支可以被调度而不是被 prompt 暗示。

这一层在实践中通常有三个切面：

- **任务组织**：把工作流表达为有向图（LangGraph 这类框架做的事）；
- **智能体协调**：多个 Agent 之间的通信拓扑与移交（handoff）规则；
- **运行时状态**：把执行过程中产生的实体与关系沉淀成可查询的结构（图记忆、GraphRAG 这类尝试）。

而这一层的演化线也很清楚：从"图作为流程编排"，走向"图作为语义模型"。前者管的是**怎么执行**，后者管的是**世界是什么**。

**边界在哪：**这也是我认为最值得说的一句话——**图给出结构，但不给出意义。**

你可以画一条从 `implement` 到 `reviewer` 的边，但图本身不知道这个 `reviewer` 和另一个子图里的 `reviewer` 是不是同一个东西；你可以给边打上 `depends_on`，但"依赖"到底是"必须先完成"还是"需要参考其结果"，图不回答。**结构正确而语义含混的系统，规模一大就会退化成一张没人敢改的连线图。**

所以第五层的真问题不在图，在**本体**：实体是什么、关系意味着什么、谁来定义、变更如何治理。这已经越过了纯技术边界。

## 五层放在一起看

| 层 | 控制对象 | 第一性原理 | 撞墙点 |
| --- | --- | --- | --- |
| Prompt | 单次推理 | 输出由输入决定，只能改输入 | 改不了"不知道" |
| Context | 喂进去的信息 | 窗口是稀缺资源，本质是资源分配 | 世界不能被喂进去 |
| Harness | 与世界的接口 | 模型只输出文本，行动=把文本解释为动作 | 单次行动无法试错 |
| Loop | 反复的节奏 | 复杂问题只能迭代逼近 | 一个循环只有一条时间线 |
| Graph | 循环间的关系 | 关系必须被显式表达在某处 | 有结构不等于有语义 |

从这张表里能读出三个结论，我认为比任何单层技巧都重要。

**第一，没有任何一层在改模型。** 五层工程全部发生在模型之外。这意味着模型能力的提升会抬高每一层的天花板，但**不会让任何一层消失**——它们解决的是结构问题，不是能力问题。

**第二，顺序是被逼出来的，不能跳。** 每一层都诞生于上一层撞墙的地方。这有极强的实践含义：**在高层解决低层的问题，是徒劳的。** 一个多智能体图跑不通，十有八九不是图画得不对，而是某个节点的工具描述有歧义（Harness 层）或者上下文里塞了噪音（Context 层）。我见过太多把架构复杂度当解药的案例——加一层图，只会把一个 prompt 层的错误放大成一个分布式系统的错误。

**第三，越往上，越不是技术问题。** Prompt 层是个人技巧，Context 层是系统设计，Harness 层是接口与权限治理，Loop 层是可靠性工程，Graph 层则直接触碰组织的语义共识——什么叫"客户"、什么叫"完成"。这也是为什么越靠上的层，护城河越深：技巧可以被抄，语义共识不能。

## 那么 Graph Engineering 是未来吗

顺着这条线，最后回答一个我常被问到的问题：**Graph Engineering 是不是当前的主流方向，是未来，还是幻影？**

我的判断是：**它既不是幻影，也不会作为一个独立的"方向"长期存在。** 但要拆开看，因为"Graph"这个词至少被四种东西共用：

- **图存储与查询**（图数据库、图算法）：早已成熟，但天花板不高，是基础设施而非增长点；
- **图作为建模手段**（GNN、风控与推荐里的关系特征）：早就是大厂标准工具箱里的东西，只是被大模型抢走了注意力；
- **GraphRAG / Agent 图记忆**：目前泡沫最重的一块。构建成本高、增量更新脆弱、"可解释性"的收益常被夸大，在多数场景下打不过一个调好的检索加重排；
- **语义层 / 本体工程**：我认为这才是真正有未来的部分。它的价值不在图这个数据结构，而在**把业务语义变成可计算的对象**。难的地方也不在技术，而在组织要达成一致。

所以更准确的说法是：**Graph 不会成为一个方向，它会被吸收。** 一部分沉进 Agent 基础设施（编排框架内置图，你甚至不需要知道它是图），一部分升维成企业的语义层。中间那层"我们来做个 GraphRAG"的独立叙事，大概率会被收敛掉。

如果要押注，我不会押"图数据库工程师"，而会押**语义建模 + 检索推理系统**这个交叉位置。

而这恰好和本文的主线是同一个结论：五层演进的方向是**约束的范围越来越大、离模型越来越远、离业务越来越近**。走到第五层，你面对的已经不是模型问题，而是"你的组织究竟怎么理解自己的业务"这个老问题。

技术会一直换名字，这个问题不会。
