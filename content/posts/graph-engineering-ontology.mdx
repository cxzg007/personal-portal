把多个 Agent 连成一张图之后，系统似乎已经有了清晰的分工：一个拆解需求，一个编写代码，一个负责审查，最后交给发布节点。图告诉我们任务如何流转，也让重试、分支和状态变化变得可见。但当第二个团队带着自己的 Agent 接进来，新的问题就出现了：双方所说的“审查”，到底是不是同一件事？

一个 Agent 所谓的审查，可能只是运行静态分析工具；另一个需要检查测试覆盖、业务约束和兼容性。它们在注册表里都可以叫 `CodeReview`，返回的状态也都可以是 `success`。如果调度器只认名称和状态，流程能够顺利走完，任务却未必真正完成。

我更愿意从这个具体问题理解语义层的价值。它要处理的是协作双方对同一个对象、能力和结果的理解，而不是给已有工作流再换一个更抽象的名字。下面以一个假设的代码审查流程展开，讨论哪些约定需要显式建模，哪些事情仍然应当留给普通代码。

## 一张图能说明什么

在这个流程里，开发 Agent 提交修改，审查 Agent 检查结果，通过后才允许进入发布阶段。节点、边和状态已经能表达执行顺序；如果审查失败，图也可以把任务送回开发节点。这一层结构很有用，它把原本藏在提示词里的控制流程移到了可观察、可测试的程序中。

但一条从“审查”指向“发布”的边，本身没有解释什么才算审查通过。是没有发现高危漏洞，还是全部测试成功？是针对当前提交，还是针对上一版代码？这些含义可能写在节点实现里，也可能散落在提示词、字段注释和团队习惯中。只要参与者固定、实现由同一个团队维护，隐含约定往往还能运转；一旦需要跨团队复用，理解偏差就会暴露出来。

这里不应把问题归咎于“图没有语义”。图数据库可以有 schema，工作流节点可以使用严格类型，边也可以携带明确的业务含义。真正需要检查的是，这些含义有没有成为参与者共享、可以验证的约定。所谓补充语义层，首先是把约定从局部实现中提取出来，让它有稳定名称、定义和维护者。

例如，与其让各个 Agent 自由填写 `reviewed: true`，不如要求审查结果指向明确的仓库和提交，注明检查范围，并关联实际产生的报告。这样，发布节点读取的就不再只是一个成功标记，而是一份可以判断是否满足发布条件的证据。

## 能力名称相同，不代表可以替代

为了发现合适的执行者，我们可以把能力组织成类型层次。按照 [OWL 2 Primer 对类层次的说明](https://www.w3.org/TR/owl2-primer/#Class_Hierarchies)，子类中的实例也属于父类。这个规则适合表达分类关系，但拿来做任务调度时，需要先弄清楚我们分类的是什么。

假设把“静态分析活动”建模成“代码检查活动”的一种。这个分类可以帮助系统找到相关工具，却不能推出“只会静态分析的 Agent 能完成整个代码审查”。前者描述活动的种类，后者要求执行者覆盖一组具体责任。类型层次没有自动补上测试验证、业务检查或人工审批，也没有证明某个工具适用于当前语言和仓库。

因此，我会把能力发现和任务准入分开。发现阶段可以宽一些，通过标签或类型层次找到候选 Agent；准入阶段则检查这次任务要求的语言、检查范围、输入版本、输出格式和执行权限。一个 Agent 可以成为候选者，同时因为缺少某项能力而不能独立承担任务。此时调度器可以组合多个执行者，也可以明确转交人工，而不是把分类关系解释成完成保证。

结果状态也需要同样的处理。工具退出码为零，只能说明这次工具调用按其约定结束；它不必然意味着没有风险，更不意味着允许发布。把“工具运行成功”“检查通过”和“业务批准”拆成不同事实，看起来增加了几个字段，却减少了后续节点猜测状态含义的空间。

## 把数据校验与知识推理分开

一旦这些事实被显式记录，下一步通常是验证。例如，一次审查必须有且只有一个责任主体，必须指向一个提交，并且附有报告。这里最容易出现的误区，是用知识推理规则替代输入数据检查。

OWL 使用开放世界假设：没有记录的事实可能只是未知，不能一概视为不存在；不同名称也不自动代表不同个体。因而，把 `owner` 声明成函数性对象属性，并不是给它加上数据库式的唯一约束。若两个名称都被记录为负责人，推理器在没有相反条件时可能推导它们指向同一个体，而不是按业务预期直接报错。这一点可以从 [OWL 的个体相等关系和属性特征](https://www.w3.org/TR/owl2-primer/#Equality_and_Inequality_of_Individuals) 中理解。

如果目标是检查提交的数据图中，某个审查记录是否恰好有一个 `owner` 值，[SHACL 的数量约束](https://www.w3.org/TR/shacl/#core-components-count) 更直接。下面是一个最小形状定义；它检查显式值的数量，不负责识别两个账号是否其实属于同一个人。

```turtle
@prefix ex: <https://example.org/review/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .

ex:ReviewShape a sh:NodeShape ;
    sh:targetClass ex:Review ;
    sh:property [
        sh:path ex:owner ;
        sh:nodeKind sh:IRI ;
        sh:minCount 1 ;
        sh:maxCount 1
    ] .
```

在包含 `ex:review42 a ex:Review` 的数据图中，没有 `owner` 值会违反最小数量约束，两个不同的 IRI 值会违反最大数量约束。只有一个 IRI 值，可以通过这里展示的检查，但仍然不能证明负责人有审查资格。资格、报告是否可信以及提交是否已变化，需要各自的规则和证据。

这也是我倾向于让两类机制各司其职的原因：推理用于从已知事实和公理得到隐含事实，校验用于判断一份待处理数据是否符合约定。即使两者使用相同的术语，也不能省略它们之间的边界。工程上还需要确定校验发生在推理之前还是之后，使用哪一版规则，避免同一份输入在不同服务里得到无法解释的结果。

## 语义如何进入真正的执行流程

有了模型，并不意味着调度器就必须在每次请求里运行完整推理。回到代码审查的例子，一条务实的路径是：注册时检查 Agent 的能力声明，接收任务时检查必要输入，选择候选者后再验证具体执行条件。规则可以由普通类型定义、数据库约束或 SHACL 实现，取决于系统是否已经使用相应的数据模型。

执行结果也要经过类似的边界。审查 Agent 返回报告后，系统先确认它针对的是当前提交，再把报告归入对应任务。若开发 Agent 又推送了新代码，旧报告可以保留，但不应继续充当新版本的放行依据。共享语义在这里最有价值的部分，是让“哪份证据证明了哪个版本的什么性质”成为可追踪关系。

真正提交发布动作之前，还需要重新检查授权与状态。此前通过的数据校验，无法阻止另一个请求在随后修改对象；模型中的“已批准”也不能替代执行系统中的并发控制。我的设计建议是把语义层给出的判断作为明确输入，由负责副作用的服务执行最终检查、记录决定并处理失败。任务调度、锁、重试和补偿仍然是工程问题。

这种接法不会要求团队一次性重建所有系统。已有 JSON 接口可以继续使用，只是字段需要映射到共同定义，版本变化也需要有迁移说明。只有当跨系统查询、关系复用或规则推导确实带来收益时，才值得进一步引入 RDF 或更强的本体表达能力。

## 共享模型也有维护成本

把约定显式化之后，争议并不会消失，它会从运行时的误解变成模型评审中的具体问题。比如，一个团队认为“审查通过”只表示自动检查完成，另一个把人工批准也包含在内。此时直接把两个概念声明为等价，可能比保留差异更危险。合理做法通常是先保留各自定义，再记录它们的包含关系、适用范围或转换条件。

这意味着语义层需要有人负责演化。能力声明增加一个必填字段，历史任务未必能立刻补齐；一个状态被拆成两个，新旧消费者也可能需要并行运行。版本、变更记录、兼容策略和真实样例，应当与模型一起维护，而不是等上线后再靠口头说明补救。

表达能力本身也有成本。更复杂的规则可能带来更难预测的推理开销和更高的排查门槛。OWL 2 DL 本身具有可判定性，而 [OWL 2 的不同 profile](https://www.w3.org/TR/owl2-primer/#OWL_2_Profiles) 提供了表达能力与计算特性的不同取舍；工程选择不能简化成“上本体就能实时推理”。对高频请求，预先计算稳定的类型关系、缓存版本化结果，可能比每次在线重新推导更合适。

如果系统只有几个固定节点，共享接口和少量校验已经足够，那么引入完整本体工具链未必划算。判断依据应当是当前反复出现的协作错误、规则重复和维护成本，而不是系统看起来还少了哪一层架构。

## 从一次真实的协作失败开始

对一个准备改进多智能体系统的团队，我会先选一条已经出过问题的流程。把失败复盘到具体字段：哪个词被双方理解成了不同含义，哪一份结果缺少来源，哪一个节点把工具成功误读成业务完成。随后只围绕这些问题补定义、加检查，再用历史失败样例确认改动能否阻止同类错误。

在代码审查案例里，第一步可能只是要求报告绑定提交版本，并拆开运行状态与审查结论。等第二个团队真正接入，再决定是否需要共享能力分类和跨系统标识。如果没有实际复用需求，先保持模型小而清楚，通常更容易看见它是否有用。

图结构负责把工作组织起来，共享语义让参与者能够理解彼此交付的东西。两者配合得好，发布节点就不必再从一个模糊的 `success` 猜测全局状态，而是能够说清楚：这次放行依据哪份报告、适用哪个提交、满足哪些条件。对我而言，这比增加一层宏大的术语更接近语义工程应当交付的结果。
