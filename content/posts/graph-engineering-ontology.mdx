> 图工程给多智能体系统搭好了骨架：任务怎么排、角色怎么接、状态往哪放。但骨架上那些节点和边到底"是什么"，至今没有人负责回答。这篇文章想说明的是，这个问题的答案在一门叫本体工程的老学科里。

## 引言：图工程之后还缺什么

多智能体工程这几年的主线很清楚，控制粒度一路上移：先是一次推理的输入（Prompt），然后是进入窗口的信息（Context），再是模型与世界的接口（Harness），接着是反复行动的节奏（Loop），最后是循环之间的关系（Graph）。

综述 arXiv 2608.21156 把这条线索完整梳理了一遍，结论落在图工程上——把智能体系统当成一张图来组织，是目前能拿到的最高抽象。

但可以接着往下问一句：图工程解决了"怎么把系统组织成一张图"，它没有解决"图上的东西是什么"。而后者会在四件事上立刻变成硬约束。

- 规模化：节点从十个涨到一千个，靠人记住每个名字的含义不成立
- 跨系统互操作：两个团队各自建的图要拼起来，字符串对不上
- 可推理：需要 CodeReview 的任务，能不能派给只声明了 StaticAnalysis 的智能体
- 自演化：让系统自己改图，得有护栏判断这次改动合不合法

这四件事，会把工程推到同一个地方。

## 从 Prompt 到 Graph：五个范式，一条主线

五个范式各自控制什么、天花板在哪，可以放在一张表里对照。

| 范式 | 控制什么 | 典型手段 | 天花板 |
| --- | --- | --- | --- |
| Prompt Engineering | 单次推理的输入 | 角色设定、示例、结构化输出 | 只能影响一次问答 |
| Context Engineering | 进入窗口的信息 | 检索、压缩、记忆、裁剪 | 窗口有限，且不管行动 |
| Harness Engineering | 模型与世界的接口 | 工具调用、沙箱、文件与终端 | 单次接口，不管节奏 |
| Loop Engineering | 反复行动的节奏 | 反思、重试、停止条件、预算 | 一个循环装不下复杂项目 |
| Graph Engineering | 循环之间的关系 | 任务 DAG、角色编排、共享状态 | 有结构，但结构缺语义 |

沿着这张表，能看出智能的三级演进。

### 模型智能

智能装在参数里，工程的全部工作是把问题描述清楚。这一级的产物是 Prompt。

### 个体智能

智能装在"模型加外部装置"里。一个可用的智能体大致等于：

```text
Agent = Loop(LLM + Harness)
```

Prompt、Context、Harness、Loop 四门手艺都服务于同一个个体。

### 系统智能

智能拆到多个角色上，单体能力不再是瓶颈，角色之间的关系才是。这一级的产物就是图。

值得注意的是，这五个范式一个都没动模型参数，全部在模型之外做工程。这说明"系统怎么组织"本身就是一门独立学问。

## 图工程组织了什么

拆开看，图工程同时在组织三样东西。

- 任务组织：用 DAG 表达执行顺序与依赖，谁先谁后、哪些可以并行
- 智能体协调：节点是角色，边是交接，把"谁做什么"显式画出来
- 运行时状态：一块共享黑板，让并发写入有确定的合并语义

这三件事今天都有成熟框架能做，比如 LangGraph：

```python
from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, END


class ArticleState(TypedDict):
    topic: str
    # 多个节点并发写同一个字段时，用 reducer 合并而不是覆盖
    notes: Annotated[list[str], operator.add]
    outline: str
    draft: str
    review: str


def research(s: ArticleState):
    return {"notes": [f"关于 {s['topic']} 的资料摘录"]}


def outline(s: ArticleState):
    return {"outline": "1. 背景 2. 论证 3. 结论"}


def write(s: ArticleState):
    return {"draft": f"基于 {len(s['notes'])} 条资料写成的初稿"}


def review(s: ArticleState):
    return {"review": "通过" if s["draft"] else "退回重写"}


g = StateGraph(ArticleState)
for name, fn in [("research", research), ("outline", outline),
                 ("write", write), ("review", review)]:
    g.add_node(name, fn)

g.set_entry_point("research")
g.add_edge("research", "outline")   # 任务依赖
g.add_edge("outline", "write")      # 角色交接
g.add_edge("write", "review")
g.add_conditional_edges(
    "review",
    lambda s: END if s["review"] == "通过" else "write",  # 循环由图控制
)
app = g.compile()
```

`ArticleState` 是运行时状态，节点是智能体，边是任务依赖。三个维度齐了，代码也能跑。

## 结构不等于语义：图工程的四条裂缝

图把"关系"表达清楚了，但没有表达"实体是什么"。节点名 `static-analysis` 对机器来说只是一个字符串，它不知道这是代码审查的一种。由此裂出四条缝。

### 互操作失效

同名异义与异名同义同时存在。A 团队的 `review` 指代码审查，B 团队的 `review` 指人工复核；A 写 `static-analysis`，B 写 `code_review`。两张图拼起来，对不上。

### 约束缺位

"一个任务最多一个负责人""高危动作必须先审批"这类规则散落在节点函数里，靠 if 语句和代码评审维持，没有统一声明的地方，也没法统一校验。

### 无法推理

一个任务声明需要 `code-review`，一个智能体声明会做 `static-analysis`。人一眼看出后者属于前者，调度器看不出来，只能返回"无可用智能体"。

### 演化中的语义漂移

让系统自己加节点、改边，几轮之后同一个概念会分裂成好几个近义名字。没有形式化定义，就没有任何东西能判定这算不算漂移。

更麻烦的是这四条缝都不报错。流程照跑，结果照出，错的是语义，这是最难查的一类故障。

| 需求 | 纯图结构能否胜任 | 说明 |
| --- | --- | --- |
| 表达执行顺序与依赖 | 可以 | DAG 的本职 |
| 并发与分支控制 | 可以 | 条件边、reducer |
| 状态持久化与回溯 | 可以 | checkpoint 机制 |
| 跨系统概念对齐 | 不行 | 字符串没有共享定义 |
| 声明式约束校验 | 不行 | 规则散在代码里 |
| 上下位推理与能力匹配 | 不行 | 不知道谁是谁的子类 |
| 自动演化不漂移 | 有风险 | 能改，但没有护栏 |

这三个"不行"，恰好是另一门工程学几十年来的主业。

## 本体工程是什么

本体（Ontology）在信息科学里的经典定义是"共享概念化的形式化显式规范"。拆成四个词看。

- 形式化：机器可读、可计算，不是文档里的自然语言约定
- 显式：概念和关系写出来，不藏在代码实现里
- 共享：多个系统共同遵循同一份定义
- 规范：带约束，能判定某条数据合不合法

它的三块基本构件是类（Class）、属性（Property）和公理（Axiom），对应的标准栈也很成熟。

- RDF 与 RDFS：三元组数据模型，以及基本的类与属性层次
- OWL：表达能力更强的公理体系，支持推理机
- SPARQL：图上的查询语言
- SHACL：数据形状校验

还有一组必须分清的概念：TBox 是概念层（什么是任务、什么是能力、谁是谁的子类），ABox 是实例层（t1 这个任务、bob 这个智能体）。图工程至今其实一直在写 ABox，缺的是 TBox。

用 owlready2 演示一遍：先声明 TBox 与一条推理规则，再放进 ABox 实例，让推理机自己补出隐含结论。

```python
from owlready2 import (Thing, ObjectProperty, FunctionalProperty,
                       get_ontology, sync_reasoner, default_world)

onto = get_ontology("http://example.org/agent#")

with onto:
    # ---------- TBox：概念与规则 ----------
    class Capability(Thing): pass
    class CodeReview(Capability): pass
    class StaticAnalysis(CodeReview): pass      # 静态分析是代码审查的一种
    class Agent(Thing): pass
    class Task(Thing): pass

    class hasCapability(ObjectProperty):
        domain, range = [Agent], [Capability]

    class requiresCapability(ObjectProperty):
        domain, range = [Task], [Capability]

    class assignedTo(ObjectProperty, FunctionalProperty):
        # Functional = 一个任务最多一个负责人，这是公理不是注释
        domain, range = [Task], [Agent]

    # ---------- ABox：实例 ----------
    bob = Agent("bob")
    bob.hasCapability.append(StaticAnalysis("sa-1"))

    t1 = Task("t1")
    t1.requiresCapability.append(CodeReview("cr-1"))

sync_reasoner(onto)   # 推理机检查一致性并补全隐含事实

# 顺着类层次查询：要 CodeReview 的任务，能匹配到只会 StaticAnalysis 的 bob
rows = list(default_world.sparql("""
    SELECT ?agent WHERE {
        ?agent <http://example.org/agent#hasCapability> ?cap .
        ?cap a ?type .
        ?type rdfs:subClassOf* <http://example.org/agent#CodeReview> .
    }
"""))
print(rows)   # [[agent.bob]]
```

注意最后那个 `subClassOf*`：查询写的是 CodeReview，命中的是 StaticAnalysis。这一步靠纯图做不到，它要求系统知道两者的上下位关系。

推理管"能推出什么"，校验管"数据合不合规"，后者交给 SHACL：

```python
from pyshacl import validate

data = """
@prefix ex: <http://example.org/agent#> .
ex:t2 a ex:Task ; ex:assignedTo ex:alice, ex:bob .   # 违规：两个负责人
"""

shapes = """
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix ex: <http://example.org/agent#> .
ex:TaskShape a sh:NodeShape ;
    sh:targetClass ex:Task ;
    sh:property [
        sh:path ex:assignedTo ;
        sh:maxCount 1 ;
        sh:message "一个任务最多只能有一个负责人" ;
    ] .
"""

ok, _, text = validate(data, shacl_graph=shapes,
                       data_graph_format="turtle", shacl_graph_format="turtle")
print(ok)     # False
print(text)   # 明确指出违反了 maxCount 约束
```

对照前面的四条裂缝：共享类层次解决互操作，OWL 公理加 SHACL 解决约束缺位，推理机解决能力匹配。第四条"演化不漂移"要留到后面讲。

## 为什么本体是图工程的归宿

图工程的三个维度往深处走，都会撞上同一件事：需要一层显式语义。

- 任务组织走向任务本体。任务不再是一个名字，而是带前置条件、产出类型、可组合关系的类，DAG 模板才有可能真正复用
- 智能体协调走向能力本体。A2A 的 Agent Card 已经把能力结构化了，但字段值仍是字符串，差的就是一层类层次
- 运行时状态走向溯源本体。状态要能回答"这个结论是谁、基于什么、在什么时候产出的"，W3C 的 PROV-O 就是为这件事定的标准
- 自演化走向本体学习。系统要自己改图，护栏只能是形式化约束，不可能是自然语言注释

| 图工程的需求 | 纯图的做法 | 本体提供的能力 |
| --- | --- | --- |
| 任务类型复用 | 复制粘贴 DAG 模板 | 任务类层次加前置条件公理 |
| 能力发现与匹配 | 字符串精确匹配 | `subClassOf*` 语义匹配 |
| 结果溯源与审计 | 自己设计日志格式 | PROV-O 标准溯源模型 |
| 结构自动演化 | 无护栏，靠人审 | SHACL 校验加推理机一致性检查 |

所以"归宿"不是修辞：这四条需求都不是外部强加的，而是图工程做深之后自己长出来的。

## 融合架构：语义层、图结构层、执行层

把两者接起来，是一个三层结构。

- 语义层（本体）回答"是什么"：类层次、属性约束、公理
- 图结构层回答"怎么组织"：节点、边、状态、条件分支
- 执行层回答"怎么做"：模型调用、工具执行、结果回写

依赖方向是单向的：图结构层的每个节点和边都要在语义层有定义；执行结果回写图之前，先过语义层的校验。

### 收益一：检索按语义收窄

同样是 GraphRAG，加了本体之后不再全图盲搜。

```python
from rdflib import Graph, Namespace, RDF, RDFS, Literal

EX = Namespace("http://example.org/agent#")
g = Graph()

# TBox：能力的类层次
g.add((EX.CodeReview, RDFS.subClassOf, EX.Capability))
g.add((EX.StaticAnalysis, RDFS.subClassOf, EX.CodeReview))
g.add((EX.Translation, RDFS.subClassOf, EX.Capability))

# ABox：三条知识片段
g.add((EX.doc1, RDF.type, EX.StaticAnalysis))
g.add((EX.doc1, RDFS.comment, Literal("Ruff 规则集与 CI 集成实践")))
g.add((EX.doc2, RDF.type, EX.Translation))
g.add((EX.doc2, RDFS.comment, Literal("术语表与译名统一方案")))
g.add((EX.doc3, RDF.type, EX.CodeReview))
g.add((EX.doc3, RDFS.comment, Literal("PR 评审清单")))

# 检索 Capability 下的 CodeReview 子树，Translation 被语义排除
q = """
SELECT ?doc ?text WHERE {
    ?doc a ?t ; rdfs:comment ?text .
    ?t rdfs:subClassOf* ex:CodeReview .
}
"""
for doc, text in g.query(q, initNs={"ex": EX, "rdfs": RDFS}):
    print(doc.split("#")[-1], text)
# doc1 Ruff 规则集与 CI 集成实践
# doc3 PR 评审清单
```

关键在于 doc2 不是被向量相似度"排到后面"，而是被语义规则明确排除。少了噪声，也少了不确定性。

### 收益二：调度按语义路由

```python
from owlready2 import Thing, ObjectProperty, get_ontology, sync_reasoner

onto = get_ontology("http://example.org/route#")

with onto:
    class Capability(Thing): pass
    class CodeReview(Capability): pass
    class StaticAnalysis(CodeReview): pass
    class Translation(Capability): pass

    class Agent(Thing): pass

    class hasCapability(ObjectProperty):
        domain, range = [Agent], [Capability]

    bob = Agent("bob")
    bob.hasCapability.append(StaticAnalysis("sa"))
    eve = Agent("eve")
    eve.hasCapability.append(Translation("tr"))

sync_reasoner(onto)


def route(required_cls):
    """按本体类层次找出能接活的 Agent，而不是比对字符串。"""
    hits = []
    for agent in onto.Agent.instances():
        for cap in agent.hasCapability:
            if required_cls in type(cap).ancestors():
                hits.append(agent.name)
                break
    return hits


print(route(onto.CodeReview))   # ['bob']  —— bob 只声明了 static-analysis
print(route(onto.Translation))  # ['eve']
```

同一个需求，字符串匹配返回空列表，语义路由返回 `['bob']`。差别就在那层 TBox。

### 代价也要说清楚

- 推理开销。OWL 完整推理的复杂度很高，工程上要退到 EL 或 RL 这类可判定子集，或者预先物化推理结果
- 建模与治理成本。本体需要有人长期维护，没有 owner 的本体一定腐化
- 收益非线性。系统小的时候本体带来的约束大于收益，规模和跨系统需求上来之后才回本

## 研究与工业界正在往哪走

### 用 LLM 降低建模成本

LLMs4OL（arXiv 2307.16648）把本体学习拆成三个可评测的任务：术语类型标注、分类体系发现、非分类关系抽取。思路是让 LLM 出草稿，把人从零起步的建模里解放出来。围绕它的社区挑战赛也在持续推动方法迭代。

### 神经符号：生成与验证分工

LLM 负责接地和生成，符号层负责验证。符号层可以是 SMT 求解器、概率逻辑引擎，也可以是推理机加 SHACL。分工原则很朴素：生成不设限，接受要过关。

### GraphRAG 的语义化

从实体共现图走向本体图。早期 GraphRAG 抽取的是"谁和谁一起出现"，加上类层次之后检索可以按概念子树收窄，全局推理能力明显好过纯向量检索。

### 能力语义化

A2A 与 MCP 解决了"能力怎么声明、怎么发现"，但停在字符串。下一步是把 Agent Card 的能力字段接到能力本体上，让 StaticAnalysis 被承认为 CodeReview 的子类。

### 工业操作层本体与自演化闭环

Palantir 的 Ontology 是目前最完整的工业样本，以本体统一企业对象与动作语义，作为 AI 的操作底座。另一条线是本体自演化：生成不设限，演化受约束，用形式化护栏防止语义漂移。

| 名称 | 方向 | 一句话贡献 | 来源 |
| --- | --- | --- | --- |
| LLMs4OL | LLM 做本体学习 | 提出用 LLM 完成术语标注、分类体系与关系抽取的本体学习范式 | arXiv 2307.16648 |
| LLMs4OL 挑战赛 | 社区基准 | 围绕 LLMs4OL 的社区赛事，推动方法迭代 | ISWC 社区赛事 |
| 神经符号 | 研究方向 | LLM 负责接地，符号层负责验证 | Neurosymbolic AI |
| microsoft/graphrag | 知识图谱增强 RAG | 用知识图谱增强 LLM，强于纯向量 RAG 的全局推理 | github.com/microsoft/graphrag |
| A2A Protocol | Agent 能力语义化 | Agent Card 实现能力发现与交互协商 | github.com/a2aproject/A2A |
| Palantir Ontology | 工业操作层本体 | 以本体统一企业对象与动作语义，作为 AI 操作底座 | palantir.com 官方文档 |

这张表放在一起看，方向是一致的：做本体的在用 LLM 降成本，做 Agent 的在给能力加语义，做 RAG 的在往图和本体上靠。

## 落地路径：四级成熟度

不建议一上手就写 OWL。可行的顺序是四级台阶。

- L0 字符串约定。节点名和状态字段靠文档约定，适合单团队、单系统
- L1 轻量 Schema。受控词表加 Pydantic 模型，把名字和结构固定下来。这是性价比最高的一级，多数团队停在这里就够
- L2 形式化本体。用 RDFS 或 OWL 定义类层次与公理，SHACL 做校验，推理机做匹配。跨团队、跨系统时才值得
- L3 自演化本体。允许系统提议新概念，但每次变更必须过一致性检查与形状校验

对应到不同角色，建议也不一样。

- 应用工程师：先把 L1 做扎实，受控词表能解决八成的对不上问题
- 平台架构师：如果平台要承载多个团队的图，L2 是迟早的事，越晚做迁移越贵
- 前沿团队：L3 值得投入，但要先有 L2 的护栏，否则自演化等于放任漂移

## 结语

图工程立起了骨架，但骨架自己不会说话。当系统需要跨团队拼接、需要推理、需要自己演化时，那层显式语义就从"可选"变成"必需"。

本体工程不是新东西，它只是终于等到了一个真正需要它的场景。
