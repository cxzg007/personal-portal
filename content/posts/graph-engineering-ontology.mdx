> 图工程给多智能体系统搭好了“任务 / 智能体 / 状态”的骨架。骨架立起来之后，还有一个问题没人回答：图上的节点和边，凭什么互相理解？本文的答案是——Graph Engineering 的尽头，是本体工程（Ontology Engineering）。

## 引言：一场关于 Agent 工程的范式之争

2026 年 8 月的一篇综述（arXiv 2608.21156）提出了一个挺有野心的主张：在 Prompt、Context、Harness、Loop 之后，智能体工程该进入下一站——**Graph Engineering（图工程）**，用一张显式、可变、能演化的图来组织任务、调度智能体、管理运行状态。

这个判断我认同。单个 Agent 扛复杂任务时会撞墙：需要不同专长、子任务互相依赖、有些环节要并行、结果得独立复核、状态要跨轮保存。这些都不是“把上下文窗口再撑大一点”能解决的，本质是**架构错配**。拆成多个专业 Agent、再用一张图组织起来，是合理的解法。

但真动手搭过的人，会在某个规模上碰到更隐蔽的麻烦：**骨架有了，图上的节点和边到底是什么意思？**

节点写着 `reviewer`，隔壁子系统也有个 `reviewer`，是同一种角色吗？边写着 `depends_on`，指的是数据依赖、控制依赖还是时序依赖？一个 Agent 声明自己会 `code-review`，调度器凭什么判断它能不能接 `static-analysis` 的活？5 个 Agent 时靠口头约定就够；50 个 Agent、两个团队的图要对接、系统要根据运行反馈自动改图时，你就会发现：图工程给了你结构，没给你**意义**。节点和边的含义，全靠开发者之间心照不宣的字符串约定在撑着。

所以本文的观点是：**图工程解决了“怎么把东西组织成图”，没解决“图上的东西是什么”。而规模化、跨系统互操作、可推理、自演化这四件事，会把工程实践一步步推向本体工程。图工程的尽头，是本体工程。**

这不是否定图工程，恰恰相反——本体工程是它顺着自身逻辑往前走的下一站。

## 1. 范式演进：从模型智能到系统智能

这几年智能的来源换了三次地方。

**第一级，模型智能。**智能装在参数里，工程的活就是把模型做大、数据喂足。谁的基座强，谁的应用就强。

**第二级，个体智能。**大家发现同一个模型，会用的人和不会用的人拉开好几倍差距。于是围绕“单个 Agent 怎么用好”长出四门手艺：Prompt 管一次推理怎么问；Context 管往窗口里塞什么；Harness 管模型和外部世界之间的接口（工具、文件、终端）；Loop 管“思考—行动—观察”这个循环怎么转、什么时候停。这一级的基本形态可以写成一行：

```text
Agent = Loop(LLM + Harness)
```

**第三级，系统智能。**单体 Agent 的天花板不在模型，而在“一个循环里塞不下一个复杂项目”。于是智能被拆到多个角色上，工程的重点从“调好一个 Agent”变成“组织好一群 Agent”——这就是图工程要干的事。

![原文配图 2](/images/graph-engineering-ontology/02-2026-09-03-20-03QxhConhsjrhmDO8.png)

**图 2 五个范式的控制粒度：从一次推理到整个系统**

**表 1 五个工程范式对比**

| **范式** | **控制什么** | **典型手段** | **天花板** |
| --- | --- | --- | --- |
| Prompt Engineering | 单次推理的输入 | 角色设定、示例、结构化输出 | 只能影响一次问答 |
| Context Engineering | 进入窗口的信息 | 检索、压缩、记忆、裁剪 | 窗口有限，且不管行动 |
| Harness Engineering | 模型与世界的接口 | 工具调用、沙箱、文件与终端 | 单次接口，不管节奏 |
| Loop Engineering | 反复行动的节奏 | 反思、重试、停止条件、预算 | 一个循环装不下复杂项目 |
| Graph Engineering | 循环之间的关系 | 任务 DAG、角色编排、共享状态 | 有结构，但结构缺语义 |

值得注意的是：这五个范式，一个都没动模型参数。它们全在模型之外做工程——这也说明“系统怎么组织”本身就是一门独立学问。

## 2. 剖析 Graph Engineering：它到底组织了什么

图工程组织三样东西。

![原文配图 3](/images/graph-engineering-ontology/03-2026-09-03-20-039LxS0YAKcxhKxAL.png)

**图 3 图工程的三个维度：任务、智能体、状态**

**任务组织。**把一个大目标拆成子任务，画成 DAG：谁在谁前面、哪几个能并行、哪一步的产出是下一步的输入。写一篇长文就是典型例子——定选题、查资料、列大纲、分节写、交叉校对、统稿，其中“查资料”和“列大纲”可以并行，“统稿”必须最后。

**智能体协调。**给每个节点配一个合适的角色：研究员、写手、审稿人、事实核查。协调要解决的是谁接哪个活、结果怎么交接、有分歧怎么裁决。

**运行时状态。**多个 Agent 得共享一块“黑板”：中间结论、引用列表、待办、失败记录。状态要能被并发追加、能回溯、能在崩溃后恢复。

![原文配图 4](/images/graph-engineering-ontology/04-2026-09-03-20-03VqJezaFQkgaYWTY.png)

**图 4 一个“写长文”任务的图化表达**

这三件事今天都有成熟框架能做，比如 LangGraph：

```python
from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, END


class ArticleState(TypedDict):
    topic: str
    # 多个节点并发写同一个字段时，用 reducer 合并而不是覆盖
    notes: Annotated[list[str], operator.add]
    outline: str
    draft: str
    review: str


def research(s: ArticleState):
    return {"notes": [f"关于 {s['topic']} 的资料摘录"]}


def outline(s: ArticleState):
    return {"outline": "1. 背景 2. 论证 3. 结论"}


def write(s: ArticleState):
    return {"draft": f"基于 {len(s['notes'])} 条资料写成的初稿"}


def review(s: ArticleState):
    return {"review": "通过" if s["draft"] else "退回重写"}


g = StateGraph(ArticleState)
for name, fn in [("research", research), ("outline", outline),
                 ("write", write), ("review", review)]:
    g.add_node(name, fn)

g.set_entry_point("research")
g.add_edge("research", "outline")   # 任务依赖
g.add_edge("outline", "write")      # 角色交接
g.add_edge("write", "review")
g.add_conditional_edges(
    "review",
    lambda s: END if s["review"] == "通过" else "write",  # 循环由图控制
)
app = g.compile()
```

`ArticleState` 是运行时状态，节点是智能体，边是任务依赖——三个维度齐了，代码也能跑。

问题在于：`notes` 里装的是什么类型的东西？`review` 这个节点需要什么能力、能不能被另一个 Agent 替上？框架一概不知。**这些语义只存在开发者脑子里。**

## 3. 图工程的语义缺口

一句话概括这一章：**结构不等于语义。**图能告诉你 A 连着 B，但不能告诉你 A 是什么、这条连线意味着什么。

![原文配图 5](/images/graph-engineering-ontology/05-2026-09-03-20-03NbtjljrcvQr67qv.png)

**图 5 结构与语义的分层：图给了骨架，语义仍然缺位**

这道缺口具体会撕出四条裂缝。

**一、互操作失效。**两个团队各建一张图，同一个词各写各的。同名异义：你的 `reviewer` 是代码审查，我的 `reviewer` 是法务合规。异名同义：你叫 `checker`，我叫 `validator`，其实是一回事。对接时只能靠人肉写映射表。

**二、约束缺位。**图能画出边，但没法声明“一个任务节点最多只能有一个负责人”“测试节点必须在实现节点之后”。这类规则只能散落在各处的 if 判断里，写漏了没人知道。

**三、无法推理。**系统不知道 `static-analysis` 是 `code-review` 的一种，所以“我要找会 code-review 的 Agent”这种请求永远匹配不上会 static-analysis 的 Agent。能力发现退化成字符串精确匹配。

**四、演化中语义漂移。**让系统自动改图，是图工程的高级目标。但字符串约定没有任何护栏——自动生成的新节点类型可能与旧的重复、冲突、含义微妙偏移，改到第 50 次时没人说得清这张图的规则还是什么。

更麻烦的是这些问题**不报错**。字段名拼错会崩，语义错位不会：`depends_on` 被一方当成数据依赖、另一方当成时序依赖，程序照跑，只是结果悄悄偏了。这种静默失败在小规模下几乎看不见，在大规模下极难定位。

![原文配图 6](/images/graph-engineering-ontology/06-2026-09-03-20-03tAVR4ie8GKznkqK.png)

**图 6 语义错位造成的静默失败**

**表 2 图结构能做什么、不能做什么**

| **需求** | **纯图结构** | **说明** |
| --- | --- | --- |
| 表达执行顺序与依赖 | ✅ | DAG 的本职 |
| 并发与分支控制 | ✅ | 条件边、reducer |
| 状态持久化与回溯 | ✅ | checkpoint 机制 |
| 跨系统概念对齐 | ❌ | 字符串没有共享定义 |
| 声明式约束校验 | ❌ | 规则散在代码里 |
| 上下位推理与能力匹配 | ❌ | 不知道谁是谁的子类 |
| 自动演化不漂移 | ⚠️ | 能改，但没有护栏 |

这三个“做不到”，恰好是另一门工程学几十年来的主业。

## 4. 什么是 Ontology Engineering

本体（Ontology）在工程语境里没那么玄：**一份机器能读、多方共同认可的概念说明书。**它由四样东西构成——

- **Class（类）**：概念本身，以及概念之间的上下位关系，例如 `StaticAnalysis` 是 `CodeReview` 的一种。
- **Property（属性）**：概念之间的关系，以及关系的定义域和值域，例如 `assignedTo` 只能从任务指向智能体。
- **Axiom（公理）**：可被机器检查和推导的规则，例如“一个任务最多一个负责人”“两个类互不相交”。
- **形式化 + 共享**：写成标准语法，而不是文档里的自然语言；由多方共同维护，而不是一个人自己约定。

第四点是关键差别。团队 wiki 上的名词解释只有人能读；本体是机器能读、能校验、能据此推理的。

![原文配图 7](/images/graph-engineering-ontology/07-2026-09-03-20-034KvT3GmRGErH3Kw.png)

**图 7 W3C 语义技术栈**

这套东西有完整标准，各管一段：

- **RDF**：最小表达单元，一切都是「主语-谓语-宾语」三元组。
- **RDFS**：加上最基础的类与属性层次（`subClassOf`、`domain`、`range`）。
- **OWL**：真正的表达力所在，背后是描述逻辑，支持基数、不相交、属性链、传递等公理，可交给推理机。
- **SPARQL**：图数据的查询语言，可以顺着类层次做语义检索。
- **SHACL**：数据形状校验，负责“这条数据合不合规”。

还有一个必须分清的概念：**TBox 是概念层（有哪些类、什么规则），ABox 是实例层（具体有哪些对象）。**图工程里的图基本都是 ABox——一堆实例和连线，缺的正是 TBox。

![原文配图 8](/images/graph-engineering-ontology/08-2026-09-03-20-03LY6F3Il7xIxjUE9.png)

**图 8 TBox 与 ABox：概念层与实例层**

用 owlready2 演示一遍：先声明 TBox 与一条推理规则，再放进 ABox 实例，让推理机自己补出隐含结论。

```python
from owlready2 import (Thing, ObjectProperty, FunctionalProperty,
                       get_ontology, sync_reasoner, default_world)

onto = get_ontology("http://example.org/agent#")

with onto:
    # ---------- TBox：概念与规则 ----------
    class Capability(Thing): pass
    class CodeReview(Capability): pass
    class StaticAnalysis(CodeReview): pass      # 静态分析是代码审查的一种
    class Agent(Thing): pass
    class Task(Thing): pass

    class hasCapability(ObjectProperty):
        domain, range = [Agent], [Capability]

    class requiresCapability(ObjectProperty):
        domain, range = [Task], [Capability]

    class assignedTo(ObjectProperty, FunctionalProperty):
        # Functional = 一个任务最多一个负责人，这是公理不是注释
        domain, range = [Task], [Agent]

    # ---------- ABox：实例 ----------
    bob = Agent("bob")
    bob.hasCapability.append(StaticAnalysis("sa-1"))

    t1 = Task("t1")
    t1.requiresCapability.append(CodeReview("cr-1"))

sync_reasoner(onto)   # 推理机检查一致性并补全隐含事实

# 顺着类层次查询：要 CodeReview 的任务，能匹配到只会 StaticAnalysis 的 bob
rows = list(default_world.sparql("""
    SELECT ?agent WHERE {
        ?agent <http://example.org/agent#hasCapability> ?cap .
        ?cap a ?type .
        ?type rdfs:subClassOf* <http://example.org/agent#CodeReview> .
    }
"""))
print(rows)   # [[agent.bob]]
```

注意最后那个 `subClassOf*`：查询写的是 CodeReview，命中的是 StaticAnalysis。这一步靠纯图是做不到的——它要求系统知道两者的上下位关系。

推理管“能推出什么”，校验管“数据合不合规”，后者交给 SHACL：

```python
from pyshacl import validate

data = """
@prefix ex: <http://example.org/agent#> .
ex:t2 a ex:Task ; ex:assignedTo ex:alice, ex:bob .   # 违规：两个负责人
"""

shapes = """
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix ex: <http://example.org/agent#> .
ex:TaskShape a sh:NodeShape ;
    sh:targetClass ex:Task ;
    sh:property [
        sh:path ex:assignedTo ;
        sh:maxCount 1 ;
        sh:message "一个任务最多只能有一个负责人" ;
    ] .
"""

ok, _, text = validate(data, shacl_graph=shapes,
                       data_graph_format="turtle", shacl_graph_format="turtle")
print(ok)     # False
print(text)   # 明确指出违反了 maxCount 约束
```

对照第 3 章的四条裂缝：共享类层次解决互操作，OWL 公理 + SHACL 解决约束缺位，推理机解决能力匹配。第四条——演化不漂移，要等到第 7 章。

## 5. 为什么是“归宿”：从 Graph Engineering 到 Ontology Engineering

图工程的三个维度，往深处走都会撞上同一件事：需要一层显式语义。

![原文配图 9](/images/graph-engineering-ontology/09-2026-09-03-20-03DrOko4PQAC89yxf.png)

**图 9 图工程三维与本体能力的对位**

**任务组织 → 任务本体。**要复用任务模板、判断两个任务是不是同一类、自动选择执行策略，就得先有任务类型的层次结构与前置条件声明，而不是一堆散装 DAG。

**智能体协调 → 能力本体。**要让请求方说“我要 code-review”、系统自动找到“会 static-analysis”的 Agent，能力必须组织成有上下位关系的概念，而不是扁平字符串。今天的 A2A Agent Card 已经把能力**结构化**了，但还没**语义化**——这一跳在 7.4 细说。

**运行时状态 → 溯源本体。**状态要能回答“这个结论是谁、基于什么、在什么时候产出的”。W3C 的 PROV-O 就是为这件事定的标准：Entity / Activity / Agent 三元组织，让审计和复盘有据可依。

**自演化 → 本体学习。**系统要自己改图，就必须有护栏来判断“这次改动合不合法”。护栏只能是形式化的约束，不可能是自然语言注释。

**表 3 图工程的需求与本体的对应能力**

| **图工程的需求** | **纯图的做法** | **本体提供的能力** |
| --- | --- | --- |
| 任务类型复用 | 复制粘贴 DAG 模板 | 任务类层次 + 前置条件公理 |
| 能力发现与匹配 | 字符串精确匹配 | `subClassOf*` 语义匹配 |
| 结果溯源与审计 | 自己设计日志格式 | PROV-O 标准溯源模型 |
| 结构自动演化 | 无护栏，靠人审 | SHACL 校验 + 推理机一致性检查 |

所以“归宿”不是修辞：这四条需求都不是外部强加的，而是图工程做深之后自己长出来的。

## 6. Ontology-Grounded Graph Engineering：融合架构

结论上不是二选一，而是分三层。

![原文配图 10](/images/graph-engineering-ontology/10-2026-09-03-20-036HhKB3Uidu3zvL8.png)

**图 10 三层融合架构：执行层 / 图结构层 / 语义层**

- **语义层（本体）**：定义有哪些类、哪些关系、哪些约束——**是什么**。
- **图结构层（图工程）**：把实例连成任务图与状态图——**怎么组织**。
- **执行层（LLM + Harness）**：真正跑起来，调模型、用工具——**怎么做**。

关系很简单：语义层给图结构层提供类型和约束，图结构层给执行层提供调度顺序，执行结果再回写到图上、并受语义层校验。

![原文配图 11](/images/graph-engineering-ontology/11-2026-09-03-20-033LfdziQRuH9b8aY.png)

**图 11 运行时闭环：执行结果回写图，语义层负责把关**

第一个直接收益：检索可以按语义收窄。同样是 GraphRAG，加了本体之后不再全图盲搜。

```python
from rdflib import Graph, Namespace, RDF, RDFS, Literal

EX = Namespace("http://example.org/agent#")
g = Graph()

# TBox：能力的类层次
g.add((EX.CodeReview, RDFS.subClassOf, EX.Capability))
g.add((EX.StaticAnalysis, RDFS.subClassOf, EX.CodeReview))
g.add((EX.Translation, RDFS.subClassOf, EX.Capability))

# ABox：三条知识片段
g.add((EX.doc1, RDF.type, EX.StaticAnalysis))
g.add((EX.doc1, RDFS.comment, Literal("Ruff 规则集与 CI 集成实践")))
g.add((EX.doc2, RDF.type, EX.Translation))
g.add((EX.doc2, RDFS.comment, Literal("术语表与译名统一方案")))
g.add((EX.doc3, RDF.type, EX.CodeReview))
g.add((EX.doc3, RDFS.comment, Literal("PR 评审清单")))

# 检索 Capability 下的 CodeReview 子树，Translation 被语义排除
q = """
SELECT ?doc ?text WHERE {
    ?doc a ?t ; rdfs:comment ?text .
    ?t rdfs:subClassOf* ex:CodeReview .
}
"""
for doc, text in g.query(q, initNs={"ex": EX, "rdfs": RDFS}):
    print(doc.split("#")[-1], text)
# doc1 Ruff 规则集与 CI 集成实践
# doc3 PR 评审清单
```

关键在于 doc2 不是被向量相似度“排到后面”，而是被**语义规则明确排除**。少了噪声，也少了不确定性。

第二个收益：调度可以按语义路由。

```python
from owlready2 import Thing, ObjectProperty, get_ontology, sync_reasoner

onto = get_ontology("http://example.org/route#")

with onto:
    class Capability(Thing): pass
    class CodeReview(Capability): pass
    class StaticAnalysis(CodeReview): pass
    class Translation(Capability): pass

    class Agent(Thing): pass

    class hasCapability(ObjectProperty):
        domain, range = [Agent], [Capability]

    bob = Agent("bob")
    bob.hasCapability.append(StaticAnalysis("sa"))
    eve = Agent("eve")
    eve.hasCapability.append(Translation("tr"))

sync_reasoner(onto)


def route(required_cls):
    """按本体类层次找出能接活的 Agent，而不是比对字符串。"""
    hits = []
    for agent in onto.Agent.instances():
        for cap in agent.hasCapability:
            if required_cls in type(cap).ancestors():
                hits.append(agent.name)
                break
    return hits


print(route(onto.CodeReview))   # ['bob']  —— bob 只声明了 static-analysis
print(route(onto.Translation))  # ['eve']
```

同一个需求，字符串匹配返回空列表，语义路由返回 `['bob']`。差别就在那层 TBox。

**代价也要说清楚：**

- **推理开销。**完整 OWL 2 DL 推理最坏情况很贵，热路径上跑不动。实践做法是用轻量子集（EL / RL），或者离线把推理结果预物化（materialization），运行时只查不推。
- **建模与治理成本。**本体是共享资产，要有人负责版本、评审、变更影响面。没有 owner 的本体一定腐化。
- **收益非线性。**单团队小系统做本体基本是纯成本；跨团队、要互操作、要自动演化时，收益才陡然上升。所以关键是判断自己在曲线的哪一段。

## 7. 最新研究与实践图景

这套思路不是我的一家之言，五个方向正在从不同起点往同一处走。

### 7.1 用 LLM 自动学习本体（LLMs4OL）：让本体自己长出来

本体几十年来最大的拦路虎是手工成本高：领域专家和知识工程师得一个概念一个概念地磨，慢且贵。LLM 恰好擅长从自然语言里抽概念、抽关系、做归类。**LLMs4OL**（奠基论文 arXiv 2307.16648）第一次把“本体学习”拆成 LLM 可执行的三类任务：

1. **术语类型标注**：给定术语，判断它属于哪个类型（如「HermiT」→「推理机」）。

2. **分类体系发现**：找出概念间的上下位关系，搭出类层次骨架。

3. **非分类关系抽取**：抽取 is-a 之外的语义关系（如「依赖」「隶属」）。

此后方法一路迭代：从零样本提示，到检索增强与少样本，再到对 LLM 生成的候选三元组施加词表与形式约束过滤。方向越来越清楚——**先放开生成，再用形式约束把关**。这正是第 6 章融合架构在“内容生产”环节的缩影。

**图 7-1 LLMs4OL：从语料到高质量本体的“生成—过滤”流水线**

### 7.2 神经符号（Neurosymbolic）：LLM 接地，符号层验证

神经符号方向和本文主张几乎同构：**LLM 负责把模糊的自然语言接地为精确的符号表示，符号系统负责一致性与可验证性。**LLM 能理解会生成但爱胡说，符号系统严谨但不懂人话，正好互补。

工程形态大同小异：LLM 产出结构化候选（声明、逻辑公式、实体映射），再交给确定性的符号层校验——可以是 SMT 求解器（Z3）检查数值与逻辑约束是否可满足，可以是概率逻辑引擎（ProbLog）做带不确定性的推理，也可以是推理机加 SHACL 检查一致性。共同信念只有一句：**LLM 要负责的结论，必须过符号层这一关。**

![原文配图 13](/images/graph-engineering-ontology/13-2026-09-03-20-03AJn64098SRgRifc.png)

**图 7-2 神经符号分工：LLM 负责接地，符号层负责把关**

### 7.3 GraphRAG 及其语义化演进：从实体图到本体图

微软的 **GraphRAG** 是这两年最出圈的“图 + LLM”实践。它抓住了向量 RAG 的短板：把文档切块、按相似度召回一堆**孤立片段**，实体之间的关系和全局语境全丢了。GraphRAG 先用 LLM 抽出知识图谱，再基于图组织上下文，所以在关系推理和全局归纳类问题上明显更强。

但它有两个已知边界：建索引的 token 成本不低；更关键的是，它构建的图多是从文本里抽的**实体共现图**，缺少形式化本体约束——节点是什么类型、类型之间有无上下位、检索该被哪些语义边界收窄，都还很松散。

下一步的演进方向因此很自然：**给 GraphRAG 的图叠一层本体。**检索就能从全图盲搜变成按类型定位，正如本章上面那段 `subClassOf*` 代码所示。从实体图到本体图，是顺理成章的一跳。

**图 7-3 向量 RAG vs GraphRAG + 本体：检索从“孤立文本块”到“语义子图”**

### 7.4 Agent 协议的能力语义化（A2A / MCP）：从能力卡到能力本体

多智能体协作绕不开一个基础问题：**一个 Agent 怎么知道另一个会什么？**A2A（Agent2Agent，现属 Linux 基金会）的答案是 **Agent Card**——一张描述能力与连接方式的名片，支持能力发现、交互协商，并且不要求暴露内部状态。它还规划了 `QuerySkill()` 用于动态查询对方技能。A2A 管「Agent 连 Agent」，MCP 管「Agent 连工具与资源」，两者互补。

这是关键一步，但目前只走到**结构化**，还没到**语义化**：能力字段本质是弱语义 JSON 字符串。A 说要 `code-review`、B 说会 `static-analysis`，协议层无法判断两者相关。下一跳是给能力一个共享本体：`StaticAnalysis ⊑ CodeReview ⊑ Capability`，于是匹配由推理完成。**从字符串标签，到 Agent Card，再到能力本体**——路径已经在真实协议里走了三分之二。

**图 7-4 A2A 能力发现：从 Agent Card（弱语义 JSON）到能力本体**

### 7.5 工业界的“操作层本体”与本体自演化

本体不只活在论文里。**Palantir Ontology** 把数据集与模型集成为组织的「操作层」，用本体统一对象、属性与动作的语义，作为 AI 和 Agent 操作企业资产的底座。趋势很清楚：当 Agent 要在真实企业里动手做事——查询、决策、触发动作——一个共享、一致、可治理的本体几乎是绕不开的地基。

把 7.1 的生成能力和“系统要自演化”的诉求接起来，就是本文架构最完整的一环：**本体自演化闭环。**系统运行中不断产生新数据与新反馈，其中藏着本体里还没有的概念；让 LLM 从中抽取候选去扩展本体，同时用 SHACL 校验与推理机一致性检查为每次扩展把关，只有不破坏一致性的变更才被合并。于是第 3 章担心的语义漂移，被关进了一个「生成不设限、演化受约束」的闭环。

## 8. 落地建议与展望

务实的问题来了：搭个多智能体系统，是不是一上来就得写一堆 OWL 公理？**恰恰相反。**本体工程最常见的翻车方式就是过度工程化——需求还没稳定就建一个「完备本体」，最后又笨重又没人维护。正确姿势是渐进式，我把它整理成一条四级阶梯。

![原文配图 17](/images/graph-engineering-ontology/17-2026-09-03-20-03VyRQElyJqTzr0rZ.png)

**图 12 本体成熟度阶梯（L0→L3）**

**L0 字符串约定。**今天大多数系统的样子：节点名、能力标签、状态字段都是裸字符串。系统小、单团队、需求稳定时，这样完全够用，别为了本体而本体。该往上走的信号是：团队开始频繁争论「这个字段到底啥意思」「这两个标签是不是一回事」。

**L1 轻量 Schema。**第一步很轻：把散落的字符串收敛成一份受控词表，给关键节点和边定义类型。哪怕只是一份共享枚举表加几个 Pydantic 模型，也能消灭大半「同名异义、异名同义」。几乎零学习成本，性价比最高，绝大多数团队该先做这一级。

**L2 形式化本体。**当需要跨团队互操作、语义匹配、自动校验合法性时，升级到 RDFS/OWL：类层次、定义域值域、基数与不相交约束，配 SHACL 校验、配推理机导出隐含事实。投入不小，换来「可推理、可校验、可互操作」三项纯图给不了的能力。原则是**只形式化真正需要推理和互操作的那部分**，其余留在 L1。

**L3 自演化本体。**让系统用 LLM 从数据与反馈中扩展本体，同时用形式约束为每次演化把关。这是前沿，也是「图工程尽头」最完整的形态。

这条阶梯的价值在于：它把「图工程 → 本体工程」从口号变成一条每步都有回报的路径，不必在 L0 和 L3 之间豪赌。多数团队的甜蜜点在 L1 到 L2 之间。

**给不同角色的一句话建议：**

- **应用工程师**：先做 L1。给能力、任务类型、状态字段定一份受控词表和类型，投入产出比最高。

- **平台 / 架构师**：要支撑多团队对接时投资 L2 的共享本体，早建比晚建好，但要克制，只建真正共享的那部分。

- **前沿团队**：盯 L3，把「生成—约束—校验」闭环接进系统的演化回路。

## 结语

回到开头那场争论。Graph Engineering 之所以击中人心，是因为它命名了一个真问题：**智能正从个体走向系统，而系统需要显式的组织结构。**这个判断是对的。

但结构只是一半。把任务、智能体、状态都画成图之后，图上节点和边的**意义**从哪来，就成了下一道关口——规模越大、互操作越深、越要求可推理与自演化，这道关口就越难绕。回答它的学问已经沉淀几十年，有 RDF / OWL / SPARQL / SHACL 完整标准栈。今天 LLMs4OL、神经符号、GraphRAG、A2A、工业操作层本体，正从五个方向朝这里合流。

所以，「Graph Engineering 之后是什么」，我的答案是：**给图一个语义地基，让它可组合、可推理、可互操作、可自我演化。图工程立起了骨架，本体工程注入了灵魂。图工程的尽头，是本体工程。**好消息是你不必等到「尽头」才动身——从写下第一份受控词表开始，这条路就在脚下了。
