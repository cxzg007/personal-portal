多智能体开发流程通常按需求拆解、代码编写、审查和发布组织节点。工作流图表达了任务的执行顺序，也使分支、重试和状态变化可以被观察。但流程结构确定之后，参与者对任务的理解仍可能存在差异，尤其是在不同团队的 Agent 接入同一系统时。

以代码审查为例，一个 Agent 只运行静态分析，另一个还检查测试覆盖、业务约束和兼容性。两者可能都注册为 `CodeReview`，也都返回 `success`。调度器若只依赖能力名称和状态值，就可能把检查范围不同的结果视为等价，并据此放行发布。

这类协作问题要求系统对对象、能力和结果建立共同定义。共享语义需要落实为可验证的接口约定：审查针对哪个版本、覆盖哪些内容，什么条件下结果可以用于发布。具体采用类型定义、数据约束还是本体模型，则取决于约定的复杂程度与复用范围。

## 1. 工作流结构与共享语义

假设开发 Agent 提交修改，审查 Agent 检查结果，通过后进入发布阶段，失败则返回开发节点。节点、边和状态已经能够表达这套控制流程，使任务流转从提示词中的隐含要求变为可以测试的程序行为。

从审查节点通往发布节点的边，还需要明确放行条件。例如，“审查通过”可能要求没有高危漏洞，也可能要求全部测试成功；报告可能对应当前提交，也可能已经落后于代码版本。这些约定若分散在节点实现、提示词和团队习惯中，跨团队接入时就很难保证一致。

图数据库的 schema、节点的严格类型以及边上的业务属性，都可以承载语义。问题在于这些定义是否被参与者共同使用，以及能否在输入和输出处验证。补充语义层，首先需要整理已有约定，为它们确定稳定名称、定义和维护责任。

例如，`reviewed: true` 只能表达一个简单状态。完整的审查记录还应关联仓库、提交版本、检查范围和实际报告。发布节点据此判断证据是否满足本次发布要求，避免从一个布尔值推测整项工作的完成情况。

## 2. 能力分类与任务准入

能力可以按类型层次组织，用于发现候选执行者。按照 [OWL 2 Primer 对类层次的说明](https://www.w3.org/TR/owl2-primer/#Class_Hierarchies)，子类中的实例也属于父类。将这种分类用于调度时，需要区分活动的种类和执行者能够承担的完整责任。

“静态分析活动”可以被建模为“代码检查活动”的子类，但这并不能推出只会静态分析的 Agent 能完成整个代码审查。完整任务可能还包含测试验证、业务检查和人工审批，并对语言、仓库及输入格式提出要求。类型归属只能提供部分匹配依据。

调度过程因此可以分为能力发现与任务准入两个阶段。发现阶段通过标签或类型层次筛选候选 Agent，准入阶段再检查语言、检查范围、输入版本、输出格式和执行权限。候选者缺少必要能力时，可以组合多个执行者或转交人工处理，不能仅凭分类关系确认任务可完成。

结果状态也应区分层次。工具退出码为零，通常只表示调用按工具约定结束；检查结论和发布批准仍需单独记录。将“工具运行成功”“检查通过”和“业务批准”分别建模，可以避免后续节点把技术执行状态直接当作业务决定。

## 3. 数据校验与知识推理

审查记录可以包含多项约束，例如必须有且只有一个责任主体、必须指向一个提交、必须附有报告。验证这些输入要求时，需要区分知识推理与数据校验的语义。

OWL 使用开放世界假设：未记录的事实可能只是未知，不同名称也不自动代表不同个体。因此，把 `owner` 声明成函数性对象属性，无法得到数据库式的唯一约束。两个名称同时被记录为负责人时，推理器在没有相反条件的情况下可能推导它们指向同一个体，而不会直接报错。这与 [OWL 的个体相等关系和属性特征](https://www.w3.org/TR/owl2-primer/#Equality_and_Inequality_of_Individuals) 一致。

若要检查数据图中的审查记录是否恰好有一个 `owner` 值，可以使用 [SHACL 的数量约束](https://www.w3.org/TR/shacl/#core-components-count)。以下形状约束负责人为一个 IRI 值，检查的是图中显式值的数量：

```turtle
@prefix ex: <https://example.org/review/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .

ex:ReviewShape a sh:NodeShape ;
    sh:targetClass ex:Review ;
    sh:property [
        sh:path ex:owner ;
        sh:nodeKind sh:IRI ;
        sh:minCount 1 ;
        sh:maxCount 1
    ] .
```

在包含 `ex:review42 a ex:Review` 的数据图中，缺少 `owner` 会违反最小数量约束，两个不同的 IRI 值会违反最大数量约束。这个形状不会识别两个账号是否属于同一个人，也不会验证负责人的审查资格。资格、报告可信度和提交版本仍需各自的规则与证据。

知识推理从已知事实和公理得到隐含事实，数据校验则判断待处理的数据是否符合约定。两者可以配合使用，但需要明确执行顺序和规则版本。先推理再校验与直接校验原始数据，可能面对不同的数据图；不同服务应采用一致的处理约定。

## 4. 执行流程中的语义约束

语义约束可以分别放在注册、任务接收和执行三个阶段。注册时检查 Agent 的能力声明，接收任务时校验必要输入，选定候选者后验证具体执行条件。这些规则可以由普通类型定义、数据库约束或 SHACL 实现，无须每次请求都运行完整推理。

审查报告返回后，系统需要确认它对应的仓库、提交和任务。开发 Agent 再次推送代码时，旧报告可以作为历史记录保留，但不能继续用于新版本的放行。报告与提交版本之间的关联，使每次发布决定都有可追踪的证据。

提交发布动作前，还需要复核授权与当前状态。前一次校验通过后，对象仍可能被其他请求修改，模型中的“已批准”也不能替代并发控制。负责执行的服务应接收语义判断的结果，完成最终检查、记录决定并处理失败；锁、重试和补偿由执行层负责。

已有 JSON 接口可以通过字段映射接入共同定义，并为版本变更提供迁移说明。当跨系统查询、关系复用或规则推导的需求增加时，再考虑引入 RDF 或表达能力更强的本体模型。工具选择应与实际使用方式相匹配。

## 5. 模型演化与维护成本

共享模型需要处理团队之间已有的概念差异。一个团队可能把“审查通过”定义为自动检查完成，另一个还包含人工批准。直接声明两者等价会丢失条件，应先保留各自定义，再描述包含关系、适用范围或转换条件。

模型变更也会影响历史数据和消费者。能力声明新增必填字段时，历史任务未必能够补齐；一个状态拆分为两个时，新旧消费者可能需要并行运行。版本、变更记录、兼容策略和真实样例，都应纳入模型的日常维护。

更强的表达能力通常伴随更高的推理和排查成本。OWL 2 DL 具有可判定性，[OWL 2 的不同 profile](https://www.w3.org/TR/owl2-primer/#OWL_2_Profiles) 则提供了表达能力与计算特性的不同取舍。高频请求可以预先计算稳定的类型关系，或缓存带版本的推理结果，再根据规则与数据的变化更新。

对于只有几个固定节点的系统，共享接口和少量校验可能已经足够。是否引入完整本体工具链，需要比较协作错误、规则重复的现有成本，以及建模、迁移和运行工具链带来的新增成本。

## 6. 语义建模的渐进实施

实施可以从一条出现过协作失败的流程开始，将问题定位到具体字段或状态。例如，能力名称含义不一致、结果缺少来源，或下游把工具运行成功误读为业务完成。围绕这些问题补充定义和检查，并用历史失败样例验证效果，较容易控制初期范围。

代码审查流程可以先要求报告绑定提交版本，并拆分运行状态与审查结论。跨团队接入后，再补充共享能力分类和跨系统标识。每次扩展都应对应实际的复用需求，以免模型维护先于业务需求变得复杂。

在这样的流程中，工作流图决定任务如何流转，共享定义约束节点交付的结果。发布记录最终能够关联到具体报告、提交和放行条件；当出现误放行时，也能沿这些关系定位失效的检查。语义建模的效果，可以通过这类实际协作结果来判断。
