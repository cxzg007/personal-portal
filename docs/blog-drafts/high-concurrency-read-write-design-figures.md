## 1. SingleFlight 请求合并对比图

**位置：第 3 节，SingleFlight 工作过程之后。**

左右两幅图使用相同的三个请求，均查询 `product:42`。左侧三个请求在缓存未命中后分别访问数据库；右侧三个请求进入同一个进程内的 SingleFlight Group，首个请求执行数据库查询，另外两个等待，再将查询结果返回给三者。完成加载后，结果写入本地缓存。

用箭头数量表现重复查询的减少。标注“同一键、同一 Group、加载期间”，避免把进程内请求合并画成跨集群的全局协调。数据库返回结果与写入缓存使用不同箭头，区分请求合并和结果缓存。

图注：同键请求在一次加载期间共享结果，后续请求由缓存承接。

## 2. 缓存旧值回填时序图

**位置：第 5 节，已替换原有四行时序表。**

参与者为读请求 A、Redis、数据库、写请求 B，时间自上而下。初始状态为 Redis 无缓存，数据库保存 `v1`。

1. A 查询 Redis，缓存未命中。
2. A 查询数据库，取得 `v1`，暂未写入缓存。
3. B 将数据库更新为 `v2`，提交成功。
4. B 删除 Redis 中的对应键，随后完成请求。
5. A 将此前读取的 `v1` 写入 Redis。

将 A 取得旧值到回填之间的等待画成较长的纵向间隔，用另一种颜色突出最后一次回填。图底部并列显示最终状态：“数据库 v2 / 缓存 v1”。

图注：写请求删除缓存后，较早开始的读请求仍可能回填旧值。

## 3. CQRS 读写模型架构图

**位置：第 6 节，商品查询示例之后。**

上方为写路径：“商品更新请求 → 写模型 → 商品数据库”。数据库变更通过变更同步链路进入投影处理，结合商家、统计等关联数据，分支更新搜索索引和商品聚合视图。下方分别画“关键词搜索 → 搜索索引”和“商品综合页 → 聚合视图”，展示两个读模型的不同用途。

写入、变更传播、查询分别使用明确的文字标签；异步传播使用虚线，标注“存在更新延迟”。不要把消息队列画成数据库提交后必然成功的隐式步骤，同步链路作为需要实现的独立部分展示。

图注：写模型维护业务数据，读模型按照查询需求组织数据，并通过变更同步更新。

## 4. 异步写入与队列积压示意图

**位置：第 8 节，每秒 1 万条输入、6 千条消费的例子之后。**

上半部分画两个时间节点：“请求受理”和“业务完成”。客户端提交请求后，先收到“处理中”；队列中的任务由消费者执行，完成后更新结果，客户端再查询结果。把首次响应与最终结果分开画，避免读者将受理速度当作处理速度。

下半部分用小幅折线图展示示例中的积压：假设初始积压为零、速率保持不变，持续输入 10,000 条/秒、处理 6,000 条/秒，则第 0、1、2、3 秒的积压分别为 0、4,000、8,000、12,000 条。横轴为时间，纵轴为待处理任务数，图名标为“恒定速率示例”。

图注：队列可以缓冲短期峰值；持续输入超过处理能力时，等待任务仍会增长。
